Реализованы `check_case(snapshot)`, CheckResult с ревизиями, хранение истории
и GET/POST `/api/v1/cases/{case_id}/checks`. Используются реальные модули

Код написан в main по выбранному Ваней процессу; исходное дерево было чистым.
Общие схемы, БД, app/main.py, данные стран и OpenAPI-снимок не менялись.

## Что проверяется

- Паспорт: подтверждение полей текущей ревизии, даты/хронология, истечение,
  соответствие профилю, срок по anchor + календарные months/days,
  возраст по years/allow_anniversary. Используется общий add_calendar_months
  из пакета 2; месяц не заменяется 30 днями. Равенство минимальному сроку
  допускается; у Франции точная десятая годовщина не допускается её правилом.
- Выписка: владелец, дата и её формат/попадание в будущее, сумма и валюта.
  Универсального возраста выписки/минимального дохода нет. Когда срок
  свежести не задан проверенным правилом, это явно отмечено как ручная сверка.
- Страховка: даты относительно поездки, территория и минимальное покрытие
  из применимого insurance_coverage. Исключения/подлинность/проверка у
  страховщика не обещаются, в результате сохраняется явное ограничение.
- Междокументные расхождения имён и отличия паспорта от профиля.
  Регистр/пробелы нормализуются; разные имена, порядок и неоднозначная
  транслитерация дают verify с origin=heuristic, без угадывания личности.

Денежные значения сравниваются Decimal из строк без float и округления.
Поддерживаемые валюты: RUB/EUR/USD/GBP/JPY/INR/EGP/ZAR/CAD/BRL/ARS/AUD/NZD/
TRY/AED/CHF/CNY. Это ограниченный набор сравнения, не полный ISO-каталог.
Неизвестная валюта -> verify. Разные валюты -> verify, сравнение не проводится;
курсы не придумываются. Подтверждённый полный минимум на поездку сравнивается
напрямую; minimum=null и period=month остаются ручным расчётом. В текущих
данных NZ задан месячный минимум — автоматического пересчёта на дни нет.
Синтетические trip-минимумы существуют только в численных unit-тестах и не
выдаются за финансовые нормы стран.

Неподтверждённое, null, невалидное, дублирующееся или подтверждённое на старой
ревизии поле никогда не используется как доказательство. Не добавляются
страховка/выписка только потому, что движок умеет их читать: наличие требуется
исключительно применимыми обязательными требованиями сценария.

## Использование правил 2 и применимости 3

Нет альтернативного реестра kind/parameters. Вызывается parse_parameters из
app/rules/schema.py. Проверки применяются к PassportValidityParameters,
PassportMaxAgeParameters, InsuranceParameters, FundsParameters.
Assertions/stay_limit/manual_review и поддерживаемость профиля вычисляет
существующий EligibilityService. Его barriers/unknown_conditions включаются
в CheckResult: они явно относятся к profile/trip/answers, а не подменяют
документные факты. Паспортная проверка с document_ids вычисляется отдельно
по подтверждённым полям документа. Противоречие профиля и документа остаётся
видимым; правильный файл не исправляет профиль автоматически.

Чтобы check_case оставался без IO и использовал именно переданный снимок,
частный _SnapshotRegistry адаптирует его реальные scenario/ruleset к уже
существующему evaluator пакета 3. Он не загружает другой каталог, не создаёт
источники/правила и не возвращает успешную фикстуру. HTTP-service загружает
снимок из настоящего FileRuleRegistry с одной ruleset_version.

Качество источников проверяется общей source_quality. Непроверенный,
конфликтующий или просроченный источник -> verify, без нового формального
барьера по этому документному правилу. Неизвестная применимость не равна no.
Все 12 текущих сценариев имеют partial coverage: coverage_gap сохраняется
даже после устранения ошибок документов. Пустой список ошибок конкретного
паспорта не означает полноту пакета или готовность к подаче.

Территория: сравнение явного ярлыка правила с полем; базовые английские
названия стран сопоставляются ISO-коду. Иная явно указанная страна -> замечание
об отличии. Worldwide/Europe/составной текст и исключения не превращаются
автоматически в покрытие Schengen/нужной страны: требуется ручная сверка.

## Python и граница пакета 4

```python
from app.checks import check_case, DocumentChecker

result = check_case(snapshot)  # общий CaseSnapshot -> общий CheckResult
# Для воспроизводимого теста можно передать aware evaluated_at.
checker = DocumentChecker()
```

InputSignature вычисляется из case_revision, фактической profile_revision,
facts_revision всех прикреплённых документов, ruleset_version и версии
алгоритма `documents-1`. Входные поля/правила не изменяются. Несогласованные
версии/привязки дают stale+verify; неподдержанное правило не пропускается молча.

После POST результат сохраняется, а проекция дела очищается:
stale=1, stale_reason=checks_updated, projection_json=NULL. case_revision при
этом не увеличивается: результат проверки является производным, иначе он
сразу сделал бы собственную подпись устаревшей. События/исход процесса не
создаются и не изменяются. История проверок сохраняется, GET берёт последний
вставленный результат, даже когда два evaluated_at совпадают.

В самостоятельном режиме ChecksService поддерживает callback CaseRebuilder.
Для фактического пакета 4 используйте CaseCheckerAdapter/CaseChecksService
из раздела интеграции выше: CaseService.snapshot → адаптер → record_check →
rebuild_case. Чистое ядро не вызывает сервис с записью, рекурсивного цикла нет.
Готовность и процесс вычисляет пакет 4; coverage gaps сохраняются.

## HTTP, хранение и устаревание

GET требует require_user, POST — require_csrf. Owner берётся из сессии;
чужой и отсутствующий case_id дают одинаковый 404. POST не принимает
snapshot/documents/rules от клиента — факты и правила загружаются сервером.
GET до первой проверки -> 404 checks_not_found; без реестра POST -> 503.
Оба маршрута возвращают общий CheckResult и Cache-Control: no-store.

Во время загрузки снимка/перед записью проверяются ревизии и состав привязок.
Документы читаются через get_confirmed_facts пакета 5 вне внешней SQL-транзакции.
Изменение входов во время вычисления -> 409 без сохранения старого результата.
Внутри записи используется короткая транзакция; долгого OCR/AI в ней нет.
Нет глобального статуса «архивный документ проверен»: результат принадлежит делу.

GET выставляет stale, если изменились профиль, дело, состав/ревизии документов,
версия алгоритма, активный набор правил, прежний stale-флаг или UTC-дата проверки.
Последнее важно для истечения паспортов/срока пересмотра источников без правок.
Старые факты/выводы при этом не переписываются. Новая активная версия требует
пересборки дела пакетом 4; POST не меняет его ruleset_version самовольно.
