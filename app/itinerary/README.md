# Пакет 7: маршрут и транзит

Реализованы PUT `/api/v1/cases/{case_id}/route` и POST
`/api/v1/cases/{case_id}/route/check`, общий RouteChecker и сохранение в
существующей таблице routes. Используются реальные аккаунты, дела 4,
архив 5, проверки 6 и события 9. AI и поиск/покупка билетов не вызываются.

## Запуск общей локальной сборки

После получения ветки Матвея с пакетами 4/9:

```bash
.venv/bin/python -m uvicorn app.itinerary.application:create_app --factory --workers 1
```

Это один сервер с пакетами 1/11/2/3/4/5/6/7/9, с обычными `/docs`,
OpenAPI и frontend через механизм Матвея. app/main.py, общие модели,
SQLite DDL и корневые зависимости этим пакетом не изменены.
Обычный app.main:app пока подключает 4/5/9, но оставляет 6/7 заглушками;
для проверки этой работы нужен указанный factory.

В него входят новые адаптеры `app/checks/integration.py`:
CaseCheckerAdapter выполняет настоящую проверку документов и возвращает
результат в подписи снимка CaseService, включая route_revision.
CaseChecksService использует snapshot/record_check/rebuild_case пакета 4.
Архив и его callback не заменяются вторым экземпляром; изменение документа
вызывает реальный пересчёт дела и проверку 6. Нормативные findings проходят
проверку ссылок CaseService. События 9 не превращаются в готовность документов.

## Что покрыто

Автоматический положительный результат ограничен взрослым гражданином и
резидентом РФ с обычным биометрическим/небиометрическим загранпаспортом,
без второго гражданства и иностранного ВНЖ, с полными согласованными
участками и пересадкой в IST или DXB: единый билет, подтверждённое
нахождение в международной зоне, отсутствие получения/перерегистрации
багажа, международные соседние участки в одном аэропорту.

Источники фактически открыты 25 октября 2026 года; checked_at записан
2026-10-25T14:04:15Z, инженерный review_after — 1 ноября 2026 года.
Срок пересмотра не обещает неизменность правил к будущему вылету.

| Источник | Подтверждённая часть / граница |
|---|---|
| [МИД Турции, FAQ](https://www.mfa.gov.tr/frequently-asked-questions.en.mfa) | Визовое условие при нахождении в транзитном зале |
| [Turkish Airlines, FAQ Istanbul Airport, Transfer Passengers №4](https://www.turkishairlines.com/en-sg/istanbul-airport/faq/) | Подтверждение условия для IST; расписание и любая конкретная стыковка не проверены |
| [МИД Турции, Russian Federation](https://www.mfa.gov.tr/visa-information-for-foreigners.en.mfa) | Только контекст туристического/делового безвизового режима; выход при транзите требует отдельной проверки |
| [МИД ОАЭ / посольство в Москве, FAQ](https://www.mofa.gov.ae/en/Missions/Moscow/Contact-Form) | Транзит без паспортного контроля; для въезда РФ — шесть календарных месяцев паспорта и лимит 90/180 |
| [Dubai Airports, Transfers](https://dubaiairports.ae/information/transfers) | Процедуры отдельных билетов/багажа в DXB и смены DXB/DWC; они требуют уточнения конкретного маршрута |

Формальный blocking выдаётся только по подтверждённому правилу паспорта
для явно заявленного и согласованного въезда в ОАЭ. Календарные месяцы
считаются общей функцией пакета 2, дата въезда — в Asia/Dubai.
Предположение о выходе из-за багажа само по себе не создаёт этот барьер.
История пребываний в текущем Route отсутствует: даже при подходящем
паспорте выход в ОАЭ остаётся needs_verification. Для выхода в Турции
положительного автоматического вывода нет.

SAW, AUH и прочие аэропорты, другие страны, внутренние участки,
отдельные билеты, смена аэропорта, неизвестные багаж/выход/тип билета,
расхождения с участками и отсутствие страны назначения дела дают
needs_verification. Ожидание от 24 часов тоже оставлено для ручной
проверки: это **инженерная граница демо**, а не юридический лимит транзита.
Минимальное время стыковки не выдумывается.

Разрешения сохраняются как переданы. Без начала действия, числа въездов
и проверяемого типа они не доказывают право въезда и не отменяют замечания;
для покрытого airside-условия приложение на них не опирается.
null не заменяется пустым списком или false в сохранённом маршруте.

covered_countries перечисляет страны, где **все** указанные пересадки
попали в проверенную автоматическую область; остальные попадают в
uncovered_countries. Это не покрытие всех визовых требований страны.
no_known_blockers относится только к перечисленным проверкам.
flight_availability всегда `not_checked`; допуск к перевозке, терминалы,
посадочный талон, бронирования и правила назначения подтверждает пользователь
с перевозчиком/официальными органами.

## Хранение, безопасность и актуальность

Владелец получается только из сессии; изменение требует CSRF. Чужой и
несуществующий case_id дают одинаковый 404. Пути файлов и owner_id
клиентом не назначаются. Ответы маршрута — no-store. Тело POST check
не используется как альтернативный маршрут/профиль/набор правил.

Участки и пересадки передаются в порядке следования. Каждому стыку
соседних участков соответствует одна Transfer; для смены аэропорта
потребуются ручная проверка и согласование данных. Отсутствующие факты
допустимы и остаются неизвестными. Нарушенная хронология, некорректные
IATA-коды, более 24 участков/пересадок или 64 KiB дают 422.
Часовые пояса обязательны, сравниваются моменты времени.

Изменившийся PUT увеличивает route_revision и case_revision,
очищает проекцию и результат маршрута, инвалидирует проверки документов
и письма, затем вызывает CaseRebuilder вне транзакции. Идентичный PUT
не меняет ревизии. Проверка маршрута не увеличивает ревизию его входов.
Перед публикацией повторно сверяются профиль, дело, маршрут и документы:
конкурирующая правка даёт 409, удаление дела — 404.

Результат и InputSignature хранятся в существующих JSON-полях routes.
Здесь ruleset_version — отдельная версия `transit:2026-10-25.1`,
algorithm_version — transit-1. Версия назначения остаётся в самом деле.
Профиль, case_revision, route_revision и ревизии прикреплённых документов
также входят в подпись. На каждую проверку качество источников пересчитывается
общей source_quality из пакета 2. Непроверенный/конфликтующий/просроченный
источник не создаёт положительного результата или нормативного барьера.

Внутренние методы ItineraryService.get_route/latest доступны пакету 4.
latest возвращает 409 route_checks_stale при stale-флаге, изменении подписи,
версии транзита/алгоритма или UTC-даты проверки; результат не подставляется
молча как актуальный. После сохранения нового маршрута без проверки — 404.
Публичный GET route/check в общем контракте не определён и не добавлен.

Callback уже вызывает настоящий CaseService; его текущая проекция ещё не
включает транзитные findings в readiness/notifications. Фронтенд получает
их из POST route/check. Для общей проекции Матвей может читать только
актуальный latest либо вызывать чистый TransitChecker; рекурсивного цикла
rebuild_case → ItineraryService.run → rebuild_case быть не должно.

## Загрузчик и передача Матвею

В пакете 2 жёстко заданы 12 стран назначения и их виды правил. Добавление
TR/AE в этот каталог нарушило бы существующую валидацию. Поэтому
TransitRuleRegistry **компонует** настоящий FileRuleRegistry, используя его
read_json с защитой от повторных ключей, CatalogManifest и source_quality.
Старые get_scenario/get_ruleset/get_sources/destinations и active_version
сохраняют поведение. Транзит читается через тот же get_ruleset(version) в
отдельном пространстве версий transit:*. Общие Rule/Ruleset/Source не менялись.

Транзитные kind/parameters ограничены Pydantic-моделями внутри этого
пакета. Отдельно проверяются ссылки, версии, дубликаты, страны и область.
Произвольные условия/исполняемый код из JSON не принимаются. Маршрутные
поля не подставляются в DSL вопросов стран назначения.

Для основного composition root Матвею передать:

```python
from app.checks.integration import CaseCheckerAdapter, CaseChecksService
from app.checks.router import router as checks_router
from app.itinerary.registry import TransitRuleRegistry
from app.itinerary.router import router as itinerary_router
from app.itinerary.service import ItineraryService

checker = CaseCheckerAdapter()
app = create_backend(feature_routers={6: checks_router, 7: itinerary_router}, case_checker=checker)
registry = TransitRuleRegistry(app.state.rule_registry)
app.state.rule_registry = registry
app.state.checks_service = CaseChecksService(app.state.case_service, checker)
app.state.itinerary_service = ItineraryService(
    app.state.database, registry, rebuilder=app.state.case_rebuilder,
)
```

Это уже выполнено в app.itinerary.application. Отдельная БД не нужна.
В pyproject.toml для wheel Матвею добавить package-data
`"data.rules.transit" = ["*.json", "*/*.json"]`; запуск из checkout работает
сейчас. Общие API DTO/DDL/эндпоинты менять не требуется.

Остающееся согласование подписи пакета 4: его текущая cases-v1 является
внешней подписью адаптера 6. При изменении алгоритма документов Матвею
нужно обновлять эту версию либо включить checker.algorithm_version в её
расчёт. Его выбор сохранённого check также пока не проверяет UTC-день
оценки, хотя GET checks это делает. Чтобы общий GET дела гарантированно
переоценивал результат на следующий день, владельцу 4 нужно учитывать
эти оси при выборе current_check. В этой работе app/cases не правился.

## Проверки и образцы

```bash

TESSDATA_PREFIX="$PWD/local_data/tessdata" .venv/bin/python -m pytest -q
.venv/bin/python tests/integration/package7_http_smoke.py

```

На проверке: 92 теста пакета 7; общий результат после интеграции —
362 passed, без пропусков. HTTP smoke, OpenAPI и pip check пройдены.
Есть одно прежнее предупреждение Starlette TestClient/httpx.

Тесты пакета используют реальные HTTP create/attach/patch/get дел 4,
архив и PDF-текст 5, настоящий движок 6, хронологию 9, перезапуск и два
аккаунта; фиктивные дела напрямую в SQL не создаются. Изменение профиля
или маршрута во время расчёта не публикует прежний результат. Проверены
все 12 направлений, поля null, раздельные билеты, область аэропортов,
просроченные/конфликтующие источники и календарная граница срока паспорта.

examples содержит три пары Route/RouteResult: airside_tr, airside_ae,
unknown_baggage. JSON получен настоящим чистым ядром на вымышленном
профиле из tests/package7/conftest.py на 25 октября 2026 года.
Это образцы ввода/вывода, не AI-ответ, не бронь и не проверка наличия рейса.
HTTP smoke запускает настоящий Uvicorn, временную SQLite и два аккаунта,
читает SAMPLE PDF, проверяет 6/7/9 и повторяет доступ после перезапуска.
