## Письма: HTTP

- `POST /api/v1/cases/{case_id}/letters`, тело `{"type":"cover_letter"}`:
  новый черновик или актуальный неизменённый черновик из кэша, HTTP 201.
- `GET /api/v1/cases/{case_id}/letters`: `{items:[Letter]}`, от старого к новому.
- `PATCH /api/v1/letters/{letter_id}`, тело `{"content":"..."}`:
  сохраняет текст, выставляет `edited_by_user=true`; длина 1–32000 символов.
- `GET /api/v1/letters/{letter_id}/file`: защищённый UTF-8 `.txt`, attachment,
  `Cache-Control: no-store`, `X-Letter-Stale: true/false`.

Запись требует cookie и `X-CSRF-Token`; чтение/скачивание — cookie.
Чужой ресурс — 404. Нельзя назначить owner, подпись, режим или флаги клиентом.
Правка сохраняет исходную подпись: редактирование устаревшего письма не
делает его актуальным. Повторная генерация не меняет строки с ручными правками;
создаётся новая версия. Скачивание устаревшего текста разрешено как экспорт
сохранённой версии; его актуальность показана в списке и заголовке.

`from_cache=true` обозначает повторное использование при POST генерации.
Обычный список/правка возвращают false. Кэш требует совпадения ревизий дела,
профиля, прикреплённых фактов, правил, маршрута, версии шаблона и настройки
модели/включения AI. Версия письма находится в `algorithm_version=letters-1-…`;
её нельзя сравнивать с `documents-1` как подпись проверки документов.
Даже при совпадающей подписи `stale=true` запрещает кэш: ручные события и
checklist могут пометить письмо устаревшим без изменения `case_revision`.
Обновление/удаление документа, профиля, поездки и привязок отменяет актуальность;
входы повторно проверяются после AI перед короткой транзакцией публикации.
Новая схема БД не нужна: используется существующая таблица letters, версия 1.

## Подтверждённые сведения и AI

Имя из сохранённого пользователем профиля сверяется с подтверждённым
паспортом при его наличии. Расхождение исключает имя из письма и добавляет
русское пояснение. Даты и цель берутся из сохранённой анкеты дела. Поля
документа читаются только через порт подтверждённых фактов актуальной ревизии.
Занятость, доход, бронирования и обстоятельства возвращения не дописываются
догадкой. Пока схема не хранит достаточных сведений, они перечисляются
как недостающие данные. Черновик не утверждает, что пакет достаточен.

В этой минимальной реализации AI компонует письмо из разрешённых английских
предложений: возвращает их порядок, проверяемый как перестановка. Произвольные
фактические утверждения модели не попадают в текст. Это ограниченный режим
композиции, а не свободное написание персонального обоснования. Текст остаётся
редактируемым пользователем. `generation_mode=ai` означает реально принятый
результат AI-композиции; `template` — локальную композицию без принятого AI-ответа.
Шаблон явно обозначен в missing_facts и интерфейсе. При timeout/некорректном
ответе также используется шаблон. Платного API/fallback нет.

Живая проба **успешна** на этом ноутбуке: Codex CLI `0.160.1`, настроенная
модель `gpt-6.1-sol`, существующий вход ChatGPT, `cover_letter` вернул
`{"paragraph_order":[0,1,2]}`. Первая схема с `uniqueItems` была отклонена;
совместимая схема проверяет уникальность в Python после ответа. Проверка
доступности и схема выполняются существующим CodexCLIProvider с отключёнными
инструментами. По умолчанию AI остаётся выключенным. Включать явно после пробы:

```bash
python scripts/probe_ai.py --model gpt-6.1-sol
VISAPILOT_AI_ENABLED=true VISAPILOT_AI_MODEL=gpt-6.1-sol ./scripts/run.sh
```

Проба использует только вымышленные сведения; credentials не копируются.
Повторный успешный ответ не гарантирует наличие лимита на следующем запросе.
Официальная документация механизма структурированного вывода CLI:
[OpenAI Docs, non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

## Frontend и передача

`frontend/dist`; явный `VISAPILOT_FRONTEND_DIST` имеет приоритет. Дизайн и новые
страницы не создавались. Исправлены стыки готовых форм: подтверждение полей
передаёт expected_facts_revision и только разрешённые поля; профиль позволяет
ответить на два обязательных вопроса области поддержки; событие не назначает
серверное source и передаёт известный исход для decision_received; скачивание
письма обращается к защищённому endpoint. Неизвестные ответы остаются null.
